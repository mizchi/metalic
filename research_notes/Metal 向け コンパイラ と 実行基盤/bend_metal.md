# Bend の現行設計と Metal を前提にした実行基盤

## 1. Bend は何を共通化し、affine 性はどこまで保証するか

### Takeaway
現行 Bend は interaction-net reduction engine ではない。依存型・affine なソースを、明示的 continuation と所有権を持つ task の flat evaluator に落とし、同じコードを CPU と GPU で実行する設計である。ただし独立性とメモリ所有権から、負荷均衡、GPU の進捗、CPU/GPU 同時実行、速度までは導かれない。

## 2. `f!(x)` と Metal の実行契約は、非同期 CPU/GPU task 構想にどう関係するか

### Takeaway
Bend の `f!` は、逐次点から GPU に処理全体を渡して結果を待つ offload 境界で、任意の非同期 task/future ではない。Metal は GPU 同士の依存処理や CPU/GPU overlap を可能にするが、UMA、ownership、可視性、resource lifetime、command ordering は別の契約として管理する必要がある。

- 論文の「CPU/GPU は同時に compute しない」は **Bend ユーザー計算の実行**について読む。host は GPU 実行中に後続 command buffer を encoding/commit できる。`GPU_DEEP=3` 個の round を `MTLEvent` chain で先行投入し、再利用する slot の旧 buffer を `waitUntilCompleted` して frontier を読み、drain を判断する。これは host 制御の overlap で、独立した Bend CPU task との overlap ではない。— [gpu_pass:4960–4998](https://github.com/bendlang/bend/blob/f0cf0a7c573145501981c44d9c33e326185f008e/bend2/comp.ts#L4960-L4998)

### Inferences
- 非同期共通 core では所有権を「host の関数 scope から消えた」時点で free せず、**最後の GPU 利用を表す completion が完了するまで保持**する必要がある。候補は affine `Task<T>` / `Future<T>` と in-flight buffer lease、読み取り borrow の終了 event、disjoint subrange capability。これは今回の設計提案であり Bend の現機能ではない。Metal 4 の unretained resource と allocator reset 契約が、この区別を具体化する。— [Apple Metal 4 core API](https://developer.apple.com/documentation/metal/understanding-the-metal-4-core-api)、[allocator reset](https://developer.apple.com/documentation/metal/mtl4commandallocator/reset())
- Kernel A → kernel B → kernel C の依存を GPU event/barrier/indirect arguments でつなげれば、A/B の結果を CPU に materialize する必要はない。CPU は completion record や最終結果だけを await できる。ただし event wait を「任意の kernel thread が安全に sleep して他 task に core を明け渡す fiber」と扱わない。Bend 型の continuation を ready queue に返すか、dispatch 境界を使う設計は区別が明確。— [single-device events](https://developer.apple.com/documentation/metal/synchronizing-events-within-a-single-device)、[Bend task delivery](https://github.com/bendlang/bend/blob/f0cf0a7c573145501981c44d9c33e326185f008e/bend2/comp.ts#L4261-L4277)
- Global spin-barrier や「他 threadgroup が必ず scheduled になる」と仮定した producer/consumer は初期設計では避けるのが保守的。これはここで確認した API の全面禁止命題ではない。command-level 同期を基本にし、persistent scheduler を導入する場合は別途 progress モデルと occupancy を検証すべき。— [MSL の進捗保証 scope: §5.2.1](https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf)
- 1つの shared corpus は移動コストを抑えるが、arena 全体への広い hazard と一括 lifetime を作りやすい。IR の世代・phase・disjoint region を型または runtime metadata に持たせれば、CPU が region A、GPU が region B を処理する overlap と、狭い barrier の生成を検討できる。単独 ownership はその基礎で、領域と時間の契約を追加する必要がある。— [Bend corpus](https://github.com/bendlang/bend/blob/f0cf0a7c573145501981c44d9c33e326185f008e/bend2/docs/BendRT/main.typ#L295-L301)、[Apple synchronization](https://developer.apple.com/documentation/metal/resource-synchronization)

### Gaps
- 参照した Apple 一次資料から、任意の別 threadgroup 間で常に相対進捗・公平性が保証されるとは確認できなかった。「絶対に一切保証がない」との普遍的断言にもしていない。wave 全体の global waiting を安全化するには device/OS ごとの追加調査と検証が必要。— [MSL §5.2.1](https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf)
- Metal 4 の低 overhead は Apple の API 目的・契約で、Bend の現 API 実装との定量比較はしていない。feature table の取得版は 2026-10-23、MSL PDF は 2026-06-04 で調査 cutoff より前。dynamic docs は 2026-11-15 取得、独立した公開日がないものは取得時点の記述。取得 URL と hash は [source-manifest.json](evidence/source-manifest.json) に保存。— [Apple feature tables](https://developer.apple.com/metal/Metal-Feature-Set-Tables.pdf)

## 3. コスト・既存計測は何を示し、GPU 上で compiler を実行する判断に何が足りないか

### Takeaway
Bend は言語全体を GPU で評価できる例として有用だが、速い実行形は「十分な幅の fork tree の末端で大きな flat loop」を回すものに寄る。UMA 下でも細かい同期往復や CPU による消費を含めて測る必要があり、既存 M5 計測は一実装の warm 同期 roundtrip の値で、Metal の最低 latency でも GPU compiler の勝利の証拠でもない。

### Cited Findings
- BendRT の掲載値は **Apple M4 Max、2026-08-31 pin、commit `64fc4b7`**。論文を収める現 HEAD の測定ではない。CPU1/CPU16/GPU/C twin を checksum 一致で比べる warm run＋timed run。例: mandelbrot 4.78/0.40/0.08/3.79 秒、queens 5.51/0.46/1.24/4.61 秒、symreg 3.31/0.29/0.54/2.22 秒。GPU が CPU16 より遅い事例も含む。— [BendRT:538–576](https://github.com/bendlang/bend/blob/f0cf0a7c573145501981c44d9c33e326185f008e/bend2/docs/BendRT/main.typ#L538-L576)
- ベンチの mandelbrot は escape 後も state を freeze して同じ ITERS 回を branchless に回す uniform instruction stream。queens は balanced prefix index space に分けても、その後の recursive backtracking が不均等になる。入力の等分割と等 work は別。— [mandelbrot:1–18](https://github.com/bendlang/bend/blob/f0cf0a7c573145501981c44d9c33e326185f008e/bench/runtime/mandelbrot/main.bend#L1-L18)、[queens:1–28](https://github.com/bendlang/bend/blob/f0cf0a7c573145501981c44d9c33e326185f008e/bench/runtime/queens/main.bend#L1-L28)
- `guide/shaders.md` は AI 執筆・人による改訂予定の tutorial と自己申告するので、そこに載る細かな timing を独立に再現した値として扱わない。ただし fork per pixel の scheduling、非 tail recursion の frame、shared `+Data` の count、広い record の stack traffic をボトルネックとして挙げる点は実装機構と整合する。「同じ意味の source なら layout/粒度を気にせず GPU が速くする」という期待の反例になる。— [tutorial provenance:1–9](https://github.com/bendlang/bend/blob/f0cf0a7c573145501981c44d9c33e326185f008e/guide/shaders.md#L1-L9)、[machine/grain:14–29](https://github.com/bendlang/bend/blob/f0cf0a7c573145501981c44d9c33e326185f008e/guide/shaders.md#L14-L29)、[ownership/cost:142–230](https://github.com/bendlang/bend/blob/f0cf0a7c573145501981c44d9c33e326185f008e/guide/shaders.md#L142-L230)
- 既存のローカル実験を再実行せず保存した。hardware は Apple M5、OS は `26.6.2 (25G83)`。一つの `MTLCommandQueue`、shared buffers、warm PSO/queue/pages、同時 in-flight は一つ。scalar は warmup100＋1000 samples。shader は `out[i]=i+bias`、preflight checksum と各 sample の result/status を検査する。測定は encode 前→commit→`waitUntilCompleted`→volatile scalar read。— [保存した benchmark source](benchmarks/bench.mm#L37)、[result JSON](benchmarks/results-final.json)
- scalar encode/submit/wait/read の p50/p95/p99 は **221.625 / 344.083 / 503.208 µs**、submit/wait は **218.708 / 341.000 / 498.750 µs**。GPU command interval の p50 は 2.166606 µs。GPU end timestamp→host wait return の p50 は **49.166614 µs**。各 distribution の中央値を足し引きして厳密な overhead 内訳にしてはいけない。— [保存結果](benchmarks/results-final.json)、[time windows:104–127](benchmarks/bench.mm)
- `gpuEndTime/gpuStartTime` は host time 秒、system mach time に相対的と公式に定義されるので、この benchmark の `mach_absolute_time` 換算との比較に根拠はある。ただし GPU end→wait return は待機・通知・host scheduling を含む経路の観測で、cache coherence のみの所要時間ではない。— [Apple gpuEndTime](https://developer.apple.com/documentation/metal/mtlcommandbuffer/gpuendtime)、[gpuStartTime](https://developer.apple.com/documentation/metal/mtlcommandbuffer/gpustarttime)、[計算箇所:119–126](benchmarks/bench.mm)
- GPU write 完了後、CPU 一 thread の `checksum`（uint32 array 全要素の uint64 加算）を計る。1 MiB / 16 MiB / 64 MiB の最初の checksum p50 は **13.041667 / 221.125 / 960.333333 µs**。待機時間はこの区間から除かれるが、load、cache/memory traffic、加算、compiler の vectorization 等を含む。「GPU→CPU の明示 copy にこの時間がかかった」とは読めない。second checksum は同じ array への即時二回目の walk。各 size は warmup5＋40 samples。— [checksum:31–35](benchmarks/bench.mm)、[array experiment:159–200](benchmarks/bench.mm)、[結果](benchmarks/results-final.json)
- 完了済み command に対する `waitUntilCompleted` と cached scalar read を 1000 回平均した ready path は p50 **0.004458 µs ≈ 4.46 ns/call**。GPU work は測定前に完了しており、これは GPU handoff latency ではない。— [ready-path source:137–154](benchmarks/bench.mm)、[結果](benchmarks/results-final.json)

### Inferences
- この M5 実験が確立するのは「shared memory でも、この warm・一個ずつ同期する実装では scalar 結果を CPU が使えるまでに約 0.22 ms median の往復が観測された」「完了後も大きな結果を読む consumer work は残る」。Metal の最小 launch latency、他の queue/signal/busy-poll/async方式、Metal 4、pipeline throughput、Bend の 3-round pipeline を評価したものではない。設計の下限として固定せず、同期方式選択の一つの baseline にする。— [実験 source と条件](benchmarks/bench.mm)、[Metal 4 queue API](https://developer.apple.com/documentation/metal/understanding-the-metal-4-core-api)
- CPU/GPU 選択の仮説は `T_CPU(W,layout)` と `T_encode + T_launch + T_GPU(W,width,divergence,layout) + T_sync + T_required_CPU_consume + T_extra_materialize` の比較。ただし実際には overlap があるので単純加算だけでなく critical path と steady-state throughput を別に扱う。値は device/OS/温度/queue state ごとに calibration し、input size だけでなく width、依存 wave 数、skew、再利用回数も特徴量候補にする。Bend の explicit bang と equal-work 契約に加える設計案である。— [Bend scheduler contract](https://github.com/bendlang/bend/blob/f0cf0a7c573145501981c44d9c33e326185f008e/bend2/docs/BendRT/main.typ#L469-L475)、[M5 baseline](benchmarks/results-final.json)
- compiler を GPU で走らせるなら、logical nanopass は検証・推論の境界、physical dispatch は bandwidth/同期の境界として分ける仮説は妥当。NodeId を保つ列への局所 rewrite、map/flag/scan/compact、独立した block の解析などは連続 dispatch または fusion を試せる。一方 pass 間の layout 変更、global fixed point、可変長 allocation、symbol lookup、diagnostics の順序は独立の難所。**Bend の実績が実証するのは runtime が再帰・allocation・ADT を GPU 上で評価できることまでで、compiler passes 全体の高速化ではない。** — [Bend の GPU 実行単位の主張:599–604](https://github.com/bendlang/bend/blob/f0cf0a7c573145501981c44d9c33e326185f008e/bend2/docs/BendRT/main.typ#L599-L604)、[Bend compiler の実際の IR/emission:17–38,2784–2818](https://github.com/bendlang/bend/blob/f0cf0a7c573145501981c44d9c33e326185f008e/bend2/comp.ts#L2784-L2818)
- 次の検証候補は (a) 同一 flat IR で CPU baseline と GPU map/compact/fixed-point の実処理を比較、(b) logical passes を個別 dispatch・同一 command buffer の連続 dispatch・fusion で比較、(c) GPU A→B→C を host readback 無しでつなぐ場合と各 pass で await する場合、(d) 独立 CPU task との overlap、(e) shared/private と buffer reuse lease の差。各比較で correctness、end-to-end latency、throughput、bytes moved、dispatch/wave count、CPU consuming time、peak memory を測る。これらは実験提案で未測定。— [CPU/GPU overlap の公式例](https://developer.apple.com/documentation/metal/synchronizing-cpu-and-gpu-work)、[event 依存の公式例](https://developer.apple.com/documentation/metal/synchronizing-events-within-a-single-device)、[既存 baseline source](benchmarks/bench.mm)

### Gaps
- 既存実験は一台・一 OS・一同期方式。外部 workload による contention、cold initialization、energy、複数 sample process、async callback の tail latency、Metal 4 比較はない。測定 flags/build invocation は `bench.mm` 内に記録されていないので、compiler optimization level を追加確認なしに断定できない。— [保存 benchmark](benchmarks/bench.mm)、[保存結果](benchmarks/results-final.json)
- 自作 core/IR に関する実装・試作・TDD は今回の範囲外。以上は実装を始める前の architectural evidence と hypotheses である。性能上の勝敗は代表 compiler workload を固定して検証するまで未確定。— [BendRT の既存結果が対象とする workload](https://github.com/bendlang/bend/blob/f0cf0a7c573145501981c44d9c33e326185f008e/bend2/docs/BendRT/main.typ#L538-L576)
