# バッファ再利用の比較検証

2026年11月15日、Apple M5／macOS 26.6.2／Xcode 26.4／MSL 4.0で、バッファ確保と arena 初期化を比較した。**大きい入力では GPU に渡す前の CPU 初期化費用が減り、既定を再利用＋選択的初期化へ変更した。** 4.1への更新は不要だった。([実装](../native/buffers.h)、[初期化の契約](../native/arena.h))

## 比較する三方式

| `buffers` | source／arena の確保 | arena 初期化 |
|---|---|---|
| `fresh` | 毎回2本確保 | 全体をゼロ埋めし、必要な sentinel を設定 |
| `reuse` | 各容量を4096 bytes以上の2の冪へ丸め、足りる間は再利用 | fresh と同じ |
| `selective`（既定） | reuse と同じ | GPU が読む前に初期値を必要とする列だけ設定 |

pool は現在の同期 driver の `Runtime` が持ち、同じ native request の複数 source・repeat 間で再利用する。source と arena は別々に拡張し、短い入力でも最大容量を保持する。現在の TS API は呼出しごとに子プロセスを起動するため、**別の API 呼出し間で pool を共有する機能はまだない**。

pool と lease はコピー・移動を禁止し、借用中の slot の再使用を拒否する。lease は GPU completion に加え、CPU の結果オブジェクト構築が終わるまで保持する。commit 後の例外でも未完了 command の完了を待ってから slot を返す。現在は一 slot・同期実行の構成であり、非同期の複数 in-flight 処理には複数 slot と別の状態遷移が必要になる。

## 初期値が必要な列を固定する

選択的初期化では control、診断 accumulator、未接続の left/right、未終端文字列用の token end、module の active／fnValid／binding／fnRoot を初期化する。空入力は容量一要素を scan するため、starts/ends の一要素もゼロにする。

rank・depth・DFA maps・node の値と span・parent・tree・scan scratch 等は、各パスが論理範囲を読む前に全要素へ書く。使用する generation/layout の異なる列へ、前の入力の値を引き継がないことが契約となる。件数は GPU control に保持し、初期化範囲を知るための中間 readback は追加していない。

`poisonBuffers: true` は取得した source／arena 全容量を `0xa5` で埋め、その後に通常の初期化を実行する検証用オプション。新規確保時の暗黙のゼロ状態に依存する漏れも検出する。計測では無効にし、arena の初期化書込み量を `initializedBytes`、検証用の汚染量を `poisonedBytes` として分ける。前者には全体ゼロ埋め後の sentinel 再書込みも含み、source copy は含まない。

25テストが通過。長→短、短→長→短、空入力、言語エラー→正常入力、未終端文字列・コメント、診断方式による layout 変更を照合し、再利用中の新規 Metal buffer 確保が0本になることも確認した。診断3方式×buffer3方式で、意図的に汚したメモリを使う **153件の Metal API/GPU validation** が通った。([差分テスト](../tests/buffers.test.ts)、[validation](../scripts/validate-metal.mjs))

## 準備費用を区間ごとに測る

`just bench-buffers` は同一 native process／library 内で3方式の順序を毎 round 回転する。各ケースは3 warmup＋30標本＋結果構築用の最後の1 round。診断は packed に固定し、各方式の token・AST・束縛・型・診断を独立した CPU oracle と照合する。

| `timingsUs` | 計測区間 |
|---|---|
| `prepareUs` | UTF-8への変換、layout と容量計画 |
| `acquireUs` | source／arena の確保・pool からの取得 |
| `initializeUs` | source copy と arena 初期化。検証時は poison も含む |
| `encodeUs` | encoder 作成、全 dispatch と barrier の予約 |
| `submitWaitUs` | commit から完了待ちが戻るまで |
| `materializeUs` | 完了後の検査、metadata と最終 AST オブジェクト構築 |

一標本の最初の5区間の和が `elapsedUs` と一致することを検査する。各区間の中央値を足して frontend 中央値にすることはできない。`submitWaitUs` は GPU work と通知・host scheduling 等を含み、readback 単独の費用ではない。`materializeUs` と最終 JSON encoding／出力、JS の JSON.parse、プロセス・library setup、run 終了時の資源解放は frontend の外である。

結果構築用 round は統計から外す。`finalMaterializeUs` はその最後の一標本であり、30標本の中央値ではない。CPU stage と GPU interval を別に測り、OS scheduling と GPU frequency は固定していない。

## 大きい入力は初期化が短くなった

試行2の256関数・77,713 bytes・48,896ノード。全方式で77 dispatch、host wait は一回。

| 方式 | frontend p50 | 確保 p50 | 初期化 p50 | encode p50 | commit/wait p50 | GPU interval p50 |
|---|---:|---:|---:|---:|---:|---:|
| fresh | 2.137 ms | 24.5 µs | 638.6 µs | 19.3 µs | 1.412 ms | 1.046 ms |
| reuse | 1.448 ms | 0.1 µs | 108.2 µs | 19.8 µs | 1.319 ms | 1.155 ms |
| selective | 1.360 ms | 0.1 µs | 19.1 µs | 17.8 µs | 1.318 ms | 1.171 ms |

試行1は fresh 1.587 ms、reuse 0.835 ms、selective 0.730 msで、初期化は約675／106／21 µsだった。全体・GPU interval は試行間でも変わるため同一試行内で比較する。今回の改善は GPU 演算が速くなったという結果ではなく、CPU 準備費用を減らした結果として読む。試行2では selective の GPU interval は fresh より長かった。

この入力の arena 初期化書込み量は **13,338,192→1,556,368 bytes**。一方、pool の確保長は logical arena 11,472,036 bytes を丸めた **16,777,216 bytes**であり、初期化量の減少を確保メモリの減少とは扱わない。容量は process RSS の測定値でもない。

1 MiBの未終端コメントは、試行2で fresh 11.011 ms、reuse 4.062 ms、selective 3.090 ms。初期化は6.747／1.174／0.173 msだった。小さい式・一関数では差がほぼなく、selective が常に最短とはならなかった。([試行1](../measurements/apple-m5-buffers-trial1.json)、[試行2](../measurements/apple-m5-buffers-trial2.json)、[計測コード](../scripts/bench-buffers.ts))

source hashes と全標本を保存している。試行1のコードは `32f715c` に保存し、試行2では既定方式と計測出力を更新したが、比較時は全方式を明示指定した。前の診断集約実験は別 build・別時刻なので、その数値を今回の A/B 基準にしていない。

## 次に残る費用

現在も API ごとの native process／Metal setup、source ごとの submit/wait、ソース byte 数を上界にした発行が残る。試行2の大モジュールでは最後の一回の AST オブジェクト構築だけで約24〜28 msかかり、最終 JSON encoding／通信／JS側の消費はさらに別である。warm frontend の数字を CLI 全体の latency にはしない。

次は常駐 native worker と summary／GPU常駐 IR の API を分けるか、GPU count に基づく indirect dispatch を比較する。いずれも MSL 4.0 で進める候補であり、この段階で4.1への更新は必須ではない。
