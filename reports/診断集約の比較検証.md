# 診断集約の比較検証

この記録は arena 再利用を導入する前の比較。続く変更と現在の準備費用は [バッファ再利用の比較検証](バッファ再利用の比較検証.md) に保存している。

2026年11月15日、Apple M5／macOS 26.6.2／Xcode 26.4 で、診断集約の3方式を実装・比較した。**MSL 4.0 で検証を続けられ、今回の変更に4.1は不要だった。** 既定方式を `packed` に変更した。CPU への中間 readback は追加していない。

## 診断の意味を保って GPU の発行回数を減らす

| 方式 | 実装 | 大きい関数モジュールの診断 dispatch |
|---|---|---:|
| `tree` | byte ごとのエラーから segment tree を一階層ずつ集約する比較基準 | 76 |
| `hierarchical` | 最大256 group が strided reduction を行い、group の結果を集約して publish | 12 |
| `packed` | エラー発生時に段階別キーへ atomic minimum、段階の末尾で publish | 4 |

`packed` は `(byteOffset << 5) | errorCode` を使う。入力上限1 MiB、code は1〜18なので u32 に収まり、`0xffffffff` の未検出 sentinel と衝突しない。ABI 生成時に全 code と容量上限を検査する。offset と code の最小順がそのまま整数キーの順になる。キーは減少するので、すでに小さい値を観測した場合は atomic read-modify-write を省ける。

構文／AST・名前解決・型のキーを分離し、先行段階の失敗を次段階より優先する。同じ段階では publish まで validity を固定するため、重複宣言が先に検出されても、より早い byte の未定義名を拾える。型違反と戻り値違反が同じ位置なら code 順を保つ。

ここで使う relaxed atomic は自己完結した整数キーの集約で、非 atomic payload の ready flag には使わない。publish は別 dispatch で、既存の serial encoder と buffer barrier が順序・可視性を確保する。MSL 4.0 を明示指定し、shader の `__METAL_VERSION__` から結果の `mslVersion` を生成する。([GPU 実装](../native/frontend.metal)、[発行と所有権](../native/main.mm)、[ABI](../native/contract.h))

## 同一プロセス内で順序を回転して比較する

`just bench-diagnostics` は8ケースについて3方式を同じ native process／library で比較し、各 round の実行順を回転する。3回 warmup、30回計測後、結果表示用の最終 round を実行する。最終 round は統計から除外する。各方式の token・AST・束縛・型・診断を独立した CPU oracle と照合する。

frontend 時間は source encoding、確保・初期化、encode/submit、最後の wait を含む。library/pipeline setup と最終 AST／JSON 化は含まない。device interval は別に測る。両者の中央値の差を readback 単独や host overhead の内訳として扱わない。OS scheduling と GPU frequency は固定していない。

試行2の256関数・77,713 bytes・48,896ノードの中央値：

| 方式 | 全 dispatch | 診断 dispatch | frontend | GPU device interval | arena bytes |
|---|---:|---:|---:|---:|---:|
| tree | 149 | 76 | 1.536 ms | 0.610 ms | 11,782,892 |
| hierarchical | 85 | 12 | 1.459 ms | 0.555 ms | 11,782,892 |
| packed | 77 | 4 | 1.401 ms | 0.530 ms | 11,472,036 |

総 dispatch は約48%減ったが、frontend の改善はこの試行で約9%。device 区間は約13%改善した。試行1も同じケースで tree 1.501 ms／0.610 ms、packed 1.404 ms／0.529 msだった。各分布の記述値であり、純粋な診断処理時間の測定ではない。

他の試行2の tree→packed：

| 入力 | frontend | GPU device interval |
|---|---:|---:|
| 長い式、51,727 bytes | 0.779→0.736 ms | 0.225→0.194 ms |
| 不正文字65,537個 | 0.854→0.783 ms | 0.216→0.178 ms |
| 1 MiBの未終端コメント | 11.148→9.772 ms | 2.191→1.416 ms |

2試行とも8ケースすべてで packed の device 中央値が最小、frontend 中央値も tree より小さかった。一方、試行1の長い式では hierarchical の frontend が packed より短く、試行間の差も大きい。全 workload の最適性は決めず、3方式を明示的に選べるように残す。([試行1の全標本・hash](../measurements/apple-m5-diagnostics-trial1.json)、[試行2の全標本・hash](../measurements/apple-m5-diagnostics-trial2.json)、[計測コード](../scripts/bench-diagnostics.ts))

## 正しさと次の検証

20テストが通過。既存の生成式・80,001ノード・複数 chunk size に加え、3方式で204通りの宣言破壊、段階優先順位、同位置 code 順、UTF-8 byte span、端数 group、エラー集中、最大 EOF offset を照合した。Metal API/GPU validation は式4件・モジュール12件×3方式の計48件でエラー報告がなかった。([差分テスト](../tests/diagnostics.test.ts)、[validation](../scripts/validate-metal.mjs))

診断キーの `packed` は複数 source をまとめる GPU batch とは別の機能である。現在も source ごとの submit/wait、毎回の arena 確保・初期化、source bytes 容量を上界にした発行が残る。次はその費用を区間ごとに計測し、arena pool と count による indirect dispatch を比較する。MSL 4.0 のまま進められる範囲である。

MSL 4.1 が必要になるのは、4.1固有の acquire/release atomic を用いた publication protocol 自体を検証するとき。GPU 内 worklist の可視性と、未実行 group を待つ処理の終了性は別に検証する。4.1への更新が必要な実験に入る前に、その要件を確認する。([4.1の仕様と現在の probe](<../research_notes/Metal GPU 言語処理系 の 設計最適化/metal_runtime.md>))
